# 통합 검증

각 서비스의 테스트가 통과해도 연결 지점은 어긋날 수 있다. 이 스킬은 **양쪽을 함께 읽고 비교**하는 데 집중한다. "API가 있는가"가 아니라 "API 응답을 소비자가 기대하는 모양대로 읽는가"를 확인한다.

## 범위 고르기

| 시점 | 범위 | 저장 |
|---|---|---|
| 모듈 완료 직후 | 그 모듈의 경계만 | `_workspace/04_qa-inspector_{모듈}.md` |
| 기능 완료 | 해당 흐름 + 수용기준 | `_workspace/04_qa-inspector_{기능}.md` |
| 마무리 | 전체 흐름 + 성공 기준 | `_workspace/05_qa-inspector_integration.md` |

## 먼저 실행

```bash
python3 .claude/skills/skrr-integration-qa/scripts/check_contracts.py
```

계약 문서끼리의 일치를 검사한다. 구현과의 일치는 확인하지 않으므로 아래 경계 검증이 따로 필요하다.

## 경계 검증표

해당 모듈의 행을 고르고 왼쪽과 오른쪽을 함께 연다.

| 경계 | 생산자 | 소비자 | 확인할 것 |
|---|---|---|---|
| 플랫폼 API ↔ 계약 | 컨트롤러, `/v3/api-docs` | `platform-api.openapi.yaml` | 경로, 메서드, 필드, 상태 코드, nullable |
| 플랫폼 API ↔ 화면 | 응답 DTO | `frontend/src/api/queries`, 컴포넌트 | 생성 타입이 최신인지, `as`·`any` 우회가 없는지, 응답 포장 해제 |
| API 전수 대조 | OpenAPI `operationId` | 프론트 호출 | 안 쓰는 API, 없는 API 호출. 의도된 경우 사유 기록 |
| 상태 전이 | `state-machines.md` | 백엔드 전이 코드 | 모든 상태 변경 지점 추적, 없는 전이와 죽은 전이 |
| 상태 ↔ 화면 | enum | 화면 분기와 문구 표 | 도달 불가능한 분기, 표시 문구 누락 |
| 202 응답 ↔ 최종 결과 | 비동기 API | 화면 | 즉시 응답에 없는 필드를 읽지 않는지 |
| SSE | `events.md`, 백엔드 발행 코드 | `useRunEvents` | 이벤트 이름과 필드, `seq` 이어받기, 종료 시 연결 해제 |
| DB ↔ 엔티티 | `schema.sql`, 마이그레이션 | JPA 엔티티 | 컬럼, enum 값, nullable. `ddl-auto: validate` 실행 |
| 백엔드 ↔ AI | `ai-api.openapi.yaml`, FastAPI | 백엔드 클라이언트 DTO | 요청·응답 필드, 작업 상태값, `retryable` 처리 |
| 백엔드 ↔ 실행기 | `runner-api.openapi.yaml` | 백엔드 클라이언트 | 이벤트 변환, 결과의 `captures`가 `crossChecks`에 연결되는지 |
| TestQuery | 스키마 | AI Pydantic 모델, 실행기 Ajv, 백엔드 `dbChecks` | 세 곳이 같은 동작과 필드를 허용하는지 |
| 카탈로그 ↔ 선택자 | 카탈로그 파일 | 생성된 `testId` | 가드가 실제로 없는 요소를 거부하는지 |
| API 명세 ↔ `responseSchema` | 대상 사이트 API 명세 | 생성된 TestQuery | 명세의 해당 상태 코드 스키마와 같은지, LLM이 지어낸 값이 아닌지 |
| `schemaCheck` | 실행기 결과 | 백엔드 저장, 리포트 | `NOT_CHECKED`를 통과로 세지 않는지 |
| 인증 | 대상 사이트 로그인 방식 | TestQuery `headers`, `secretCaptures` | 토큰이 전달되는지, 로그와 HAR에 남지 않는지 |
| S3 키 | 백엔드 업로드 | AI 읽기, 실행기 업로드 | `architecture.md` 키 구조, presigned 권한과 만료 |
| 설정 이름 | 각 서비스 설정 코드 | ConfigMap, Secret, `.env.example` | 환경변수 이름과 기본값, 실행기에 비밀값이 없는지 |
| 제한값 | `architecture.md` | UI, nginx, Spring, AI, 실행기 | 20MB, 500자, 가드 3회, 시간 제한이 모두 같은지 |
| 경로 | Ingress, nginx | 프론트 기본 경로, 컨트롤러 매핑 | `/api/v1`이 끝까지 이어지는지 |
| 요구사항 ID | 대상 사이트 `FR-CART-*` | 플랫폼 `FR-01` 문서 | 두 체계를 섞지 않았는지 |

## 화면 검증

`harness/references/export/`의 PNG와 실제 화면을 나란히 비교한다. `harness/context/ui-screens.md`의 항목을 확인하고 달라진 점을 스크린샷과 함께 기록한다. 예시 데이터 차이는 결함이 아니다. 브라우저로 확인하지 못했으면 미검증이다.

## 수용기준

| ID | 확인 |
|---|---|
| FR-01 | 필수 문서를 하나씩 빼고 등록 → 거부되고 빠진 항목이 표시됨 |
| FR-02 | 평가 세트로 Top 3 포함률 90% 측정 |
| FR-03 | 모호한 요청 10건 중 8건 판정. 미승인 시나리오 실행이 거부됨. 승인 후 수정하면 승인이 풀림 |
| FR-04 | 승인 시나리오 전체가 변환되고 `tsc` 통과 |
| FR-05 | 실행 중 API 호출과 로그가 화면에 나타남. 연결을 끊었다 이어도 유실·중복 없음 |
| FR-06 | 심은 장애에서 실패 판정과 원인 후보가 나오고 근거가 실제 값임 |
| FR-07 | 리포트 수치가 원본 데이터와 일치 |
| NFR-01 | 같은 입력을 반복 실행해 정상 케이스의 판정이 안정적임 |

실패 시나리오도 확인한다: AI 서버 다운(`ERROR`, 재시작 후 복구), 실행기 다운, 대상 사이트 접속 불가, 실행 중단, 중단 후 데이터 정리, 허용되지 않은 대상 URL.

## 안전 확인

- 실행기가 임의 코드를 받는 경로가 없는지, 값 주입 시도가 코드가 되지 않는지
- 실행기 파드에 비밀값이 없고, 내부 서비스로의 접속이 막히는지
- 저장소와 로그, spec에 비밀값이 없는지. `git` 추적 파일에서 키 형태를 검색한다
- 대상 DB에 쓰는 경로가 조회 API에 없는지
- 치환 값으로 경로를 바꿔 허용 호스트 밖으로 나갈 수 없는지

판정 정확도도 확인한다: 응답 필드를 일부러 빼거나 타입을 바꾼 장애, 세 값이 같은 값으로 틀린 장애를 심어 각각 `API_SCHEMA_MISMATCH`와 `MISMATCH`로 잡히는지 본다.

## 보고 형식

```markdown
# QA: {범위}

## 결론
통과 N · 실패 N · 미검증 N

## 실패
### Q1. {한 줄 요약}
- 경계: {생산자} ↔ {소비자}
- 근거: `path:line` 대 `path:line`
- 재현: {명령 또는 절차}
- 담당: {에이전트}
- 수정 방향: {구체적으로}

## 통과
- {항목}: {근거}

## 미검증
- {항목}: {실행하지 못한 이유, 필요한 조건}
```

통과에도 근거를 적는다. 근거 없는 통과는 미검증으로 옮긴다. 평가 수치에는 조건(모델, 표본, 날짜)을 함께 적는다.

## 실패 처리

담당자에게 파일:라인과 수정 방향을 보낸다. 경계 문제는 양쪽 모두에게 보내고, 어느 쪽이 계약과 다른지 명시한다. 계약 자체가 문제면 `contract-architect`에게 보낸다. 수정 후 해당 항목을 다시 검증하며, 같은 항목이 2회 수정 후에도 실패하면 리더에게 올린다.
