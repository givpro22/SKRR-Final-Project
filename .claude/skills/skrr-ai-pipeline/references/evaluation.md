# 품질 평가

요구사항서 수용기준과 성공 기준을 재현 가능하게 측정한다. 평가 자료는 `ai/evals/`에 둔다. 팀이 직접 만드는 자료이므로, 없으면 지어내지 말고 아래 형식으로 요청한다.

## 지표

| 기준 | 목표 | 입력 | 계산 |
|---|---|---|---|
| FR-02 검색 | 상위 3개에 90% 이상 | 기능 이름 질의 + 정답 요구사항 ID | 정답이 Top 3 안에 든 비율 |
| FR-03 정제 | 10건 중 8건 이상 | 모호한 요청 10건 + 평가 기준 | 사람 판정 또는 근거 일치. 판정자를 기록 |
| FR-04 코드화 | 100% | 승인된 시나리오 전체 | TestQuery 생성 + 컴파일 통과 비율 |
| 완주 | 10건 중 8건 이상 | 평가 요청 10건 | 리포트까지 `ERROR` 없이 도달 |
| 탐지율 | 80% 이상 | 장애 목록 | 장애 주입 후 관련 케이스 `FAILED` 비율 |
| 오탐률 | 5% 이하 | 장애 없는 대상 사이트 | 정상 케이스가 `FAILED`인 비율 |
| 원인 1순위 | 70% 이상 | 탐지된 장애 + 정답 원인 | `rank=1`이 정답과 일치하는 비율 |

## 데이터 형식

```yaml
# ai/evals/retrieval.yaml
- query: 장바구니 수량 변경
  expected: [FR-CART-02]
```

```yaml
# ai/evals/faults.yaml
- faultId: cart-merge-overwrite
  description: 병합 시 수량을 합산하지 않고 덮어씀
  affectedRequirements: [FR-CART-03]
  expectedFailingCases: [동일 상품 수량 합산]
  rootCause: 병합 API가 동일 SKU 수량을 합산하지 않음
```

## 보고 규칙

결과마다 다음을 함께 적는다. 이 값이 다르면 수치를 비교할 수 없기 때문이다.

- 날짜, 커밋, 모델과 임베딩 이름, `topK`, 프롬프트 버전
- 표본 수와 분자, 분모 (예: 8/10)
- 실패 사례 목록

`LLM_PROVIDER=fake`로 낸 수치는 파이프라인 동작 확인일 뿐 품질 수치가 아니다. 실제 모델로 측정하지 않았으면 "미측정"으로 적는다.

표본이 10건 수준이면 1건 차이로 기준 통과가 갈린다. 프롬프트를 바꿀 때마다 같은 평가 세트로 다시 재고, 평가 세트 자체에 맞춰 프롬프트를 고치는 과적합을 경계한다.
